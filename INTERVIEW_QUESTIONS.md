# Interview Questions for Student Saarthi

This document outlines potential interview questions and topics based on the architecture, tech stack, and features of the **Student Saarthi** application.

## 1. Next.js 16 & React Architecture
**Q1: Student Saarthi uses Next.js 16 with the App Router. What are the primary benefits of the App Router over the older Pages Router, especially for a project like this?**
**Answer:** The App Router introduces React Server Components by default, which means components render on the server, sending less JavaScript to the client. This results in faster initial page loads (crucial for students on lower-end devices). It also provides a more powerful nested layout system, built-in support for streaming (allowing bits of the UI to appear incrementally), and highly optimized data fetching paradigms using standard `fetch` APIs without relying on older Next.js specifics like `getServerSideProps`.

**Q2: I see you implemented middleware for Supabase Auth in `proxy.ts`. Can you explain the role of Next.js Middleware and why you chose to handle authentication checks there?**
**Answer:** Next.js Middleware runs globally across the application before any request completes. By putting authentication logic in `proxy.ts`, I can intercept requests at the edge. If an unauthenticated user attempts to visit a protected route (such as `/timeline`, `/quiz`, or `/guidance`), the middleware checks their session cookies and redirects them securely to the `/login` page *before* any React component rendering or database querying begins. This provides a robust security layer and prevents unauthorized UI flashing.

**Q3: How do you decide which components should be Server Components (`Server`) and which should be Client Components (`'use client'`) in this application?**
**Answer:** The default is always Server Components. I use them for components that fetch data, interact with the database (Supabase), or need access to secure backend environment variables (like calling the Gemini API). I only opt into Client Components (using the `'use client'` directive) when a component absolutely requires browser interactivity: managing state (`useState`, `useEffect`), reacting to user events (onClick, onChange), using form frameworks (`react-hook-form`), or accessing browser-specific APIs like the Web Speech API used in the voice input functionality.

## 2. Artificial Intelligence (Gemini Integration)
**Q4: How did you integrate the Google Gemini 1.5 Flash model? Describe the prompt engineering approach you used to generate career guidance.**
**Answer:** I utilized the `@google/generative-ai` SDK on the server-side. The prompt engineering approach heavily relies on zero-shot prompting combined with explicit system formatting instructions. The system prompt instructs Gemini to act as an expert career counselor for Indian students and crucially, mandates that the response must be returned solely as a structured JSON object. I provided a strict JSON schema within the prompt, defining exact keys like `stream`, `rationale`, `subjects`, and `careers`. This ensures the AI's output is predictable and can be parsed programmatically in my React components without breaking the UI.

**Q5: AI APIs can sometimes be slow or fail. How do you handle error states, timeouts, or malformed JSON responses from the Gemini API when generating guidance?**
**Answer:** On the backend API Route, the `JSON.parse()` call is wrapped in a robust try-catch block to gracefully handle situations where the AI 'hallucinates' invalid JSON. If parsing fails, or if the API times out, the backend returns a clear 500 error status. On the frontend, I manage a `isLoading` state to display a loading spinner while waiting. If the API returns an error, my implementation catches the exception and displays an informative fallback UI using components like `sonner` for toast notifications, prompting the student to try generating the guidance again.

## 3. Database & Authentication (Supabase)
**Q6: You migrated to Supabase Auth using Server-Side Rendering (SSR). What are the security and user experience benefits of SSR authentication compared to purely client-side authentication?**
**Answer:** SSR authentication allows the Next.js server to read the user's authentication state on the very first incoming request via secure, HTTP-only cookies. Pure client-side auth relies on executing JavaScript to check local storage, which often leads to a "flicker" where an unauthenticated page flashes briefly before the user is redirected. SSR auth prevents this entirely, providing a seamless user experience. Furthermore, HTTP-only cookies protect session tokens from being stolen by Cross-Site Scripting (XSS) attacks, making the application inherently more secure.

**Q7: How did you implement user profile creation upon signup?**
**Answer:** User profile creation is best handled dynamically at the database level rather than trusting the client. The most robust approach using Supabase is to create a Database Trigger connected to a function attached to the `auth.users` table. Whenever a new row is reliably inserted by Supabase Auth (meaning the user successfully signed up), the trigger executes a PostgreSQL function that automatically inserts a corresponding row into a public `profiles` table using the newly generated `uid`. This ensures referential integrity and guarantees every authenticated user has a profile record.

## 4. Voice & Interactive Features
**Q8: The app features Hindi speech output using Google Cloud TTS. Walk me through the data flow from when the AI generates the text to when the user hears the audio.**
**Answer:** Once the Gemini AI generates the career guidance payload on the backend, the text is sent back to the React client. When the user requests audio, a Client Component triggers an API call to my custom Next.js endpoint (`/api/tts`), sending the text payload. The Next.js server authenticates securely with Google Cloud using a service account JSON file kept in specific environment variables. It requests audio synthesis specifically targeting a Hindi voice model. Google Cloud returns an audio buffer to my server, which my Next.js route handler then forwards back to the client as an `audio/mpeg` response. The React client intercepts this stream, creates a Blob URL, and plays it natively via an HTML5 `<audio>` element or JavaScript's internal `Audio` object.

**Q9: For the Speech-to-Text feature, you used the Web Speech API. What challenges did you face with browser compatibility, and how do you handle browsers that do not support this API?**
**Answer:** The primary challenge is that the Web Speech API (`SpeechRecognition` or `webkitSpeechRecognition`) is not universally supported. For instance, it frequently lacks support on Mozilla Firefox or older versions of iOS Safari. To handle this gracefully, I implemented a feature check (`typeof window !== 'undefined' && ('SpeechRecognition' in window || 'webkitSpeechRecognition' in window)`) before attempting to mount or render the microphone interface. If the API is missing, the app gracefully degrades, hiding the voice input buttons and ensuring the standard text keyboard input remains fully functional and accessible as the primary fallback.

## 5. Styling & the UI
**Q10: You've implemented a Dark/Light mode toggle utilizing `next-themes` and Tailwind CSS v4. How does `next-themes` integrate with Tailwind's dark mode strategy?**
**Answer:** Tailwind CSS's manual dark mode relies on a specific class (like `dark`) being applied to a parent element, typically the `<html>` or `<body>` tag. `next-themes` manages the logic of detecting the user's system preferences via `window.matchMedia` and persisting their manual theme overrides in local storage. Once configured, a `ThemeProvider` wraps the Next.js application, and `next-themes` automatically injects the `dark` class onto the root HTML element when dark mode is active. This allows Tailwind's `dark:` utility classes (like `dark:bg-slate-900`) throughout the app to seamlessly override the default light styling without writing custom CSS logic.

**Q11: The project uses `shadcn/ui` for components. Why choose `shadcn/ui` over a traditional component library like Material UI or Chakra UI?**
**Answer:** `shadcn/ui` takes a unique approach: it is a collection of beautifully designed, accessible, reusable components that you copy and paste directly into your project rather than installing as an opaque npm dependency. I chose it for Student Saarthi because it provides absolute control over the code and styling. It is built directly on top of Radix UI primitives (for strict web accessibility) and utilizes standard Tailwind CSS for styling. This ensures my final bundle only contains the components I've actually used, sidestepping the bloat and difficult customization often associated with traditional, monolithic component libraries.

## 6. General Software Engineering
**Q12: If we wanted to scale this app to support 10,000 concurrent students taking the quiz and requesting AI guidance simultaneously, what potential bottlenecks would you anticipate and how would you address them?**
**Answer:** Given the architecture, several bottlenecks exist at scale. First, connecting natively to Postgres creates connection overhead; I would need to ensure Supabase's PGBouncer/connection pooling is enabled to handle thousands of concurrent queries without exhausting database limits. Second, Google Gemini and Google Cloud TTS impose strict API Rate limits (requests per minute). To mitigate this, I would implement robust Redis-based rate limiting on my Next.js API endpoints. Finally, generating guidance computationally is slow. Under extreme load, Vercel serverless function timeouts become an issue. I would transition from synchronous HTTP replies to asynchronous background processing (e.g., passing tasks to a queue like Inngest, notifying the client via SSE/WebSockets when guidance is ready) and implement strict caching for identical queries/outputs.

**Q13: What was the most challenging technical hurdle you faced while building Student Saarthi, and how did you overcome it?**
**Answer:** *(Example Candidate Response)* "One of the most complex hurdles was migrating Supabase Auth from standard client-side storage to Server-Side Rendering (SSR). Next.js App Router strictly separates Server and Client environments. Initially, reading auth cookies in Server Components resulted in mismatching states because the middleware wasn't aggressively intercepting route changes correctly on soft-navigations. I had to deeply audit how Next.js Middleware (`proxy.ts`) intercepted token refresh requests. By strictly following the `@supabase/ssr` documentation and ensuring that the middleware not only validates the session but reliably writes any refreshed tokens back onto the Response Cookie object, I was able to secure the application entirely server-side without flashing unauthenticated screens to the user."
